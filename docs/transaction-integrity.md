# 거래 정합성 — 행 잠금 · 멱등성 · 복식부기 · 임시조치

[README](../README.md) 2절의 상세다. 설계 근거, 대조군을 포함한 검증, 부하 측정을 담는다.

## 2-1. 동시 이체와 행 잠금

이체는 "읽고 → 판단하고 → 쓰는" 연산이다. 잔액 10만원 계좌에 8만원 이체 두 건이
동시에 들어오면 둘 다 "잔액 10만원"을 읽고 둘 다 통과시켜, 잔액이 음수가 되거나
한쪽 차감이 다른 쪽 쓰기에 덮여 사라진다(lost update). 애플리케이션 레벨 `if` 문으로는
막을 수 없다 — 두 요청 모두 자기 시점에서는 조건을 만족하기 때문이다.

```python
# app/ledger.py — 데드락 방지를 위해 항상 account_id 오름차순으로 잠근다
for account_id in sorted(set(account_ids)):
    db.query(models.Account).filter(...).with_for_update().one_or_none()
```

- **`SELECT ... FOR UPDATE`** 로 계좌 행에 배타 잠금. 읽기·판단·쓰기가 한 트랜잭션에
  들어가므로 중간 상태가 다른 요청에 보이지 않는다.
- **잠금 순서 고정**: A→B와 B→A 이체가 각자 출금 계좌부터 잠그면 서로를 기다리며
  데드락이 된다. 출금/입금 구분 없이 계좌번호 오름차순으로 잠가 순환 대기를 없앤다.
- **원장 금액은 `NUMERIC(18,2)`**: 이진 부동소수는 0.1을 정확히 표현하지 못해 잔액을
  더하고 빼는 과정에서 오차가 누적된다. 합계가 맞아야 하는 테이블이므로 십진 고정소수를 쓴다.
- **잔액 변경과 거래 기록을 한 커밋으로**: 따로 커밋하면 "잔액은 줄었는데 거래 기록이
  없는" 상태가 존재할 수 있다.

**검증** — `tests/test_concurrency.py`가 같은 계좌에 이체 12건을 동시에 던진다.
잔액이 3건분뿐이므로 성공은 최대 3건이어야 하고, 줄어든 잔액이 성공 건수와 정확히
일치해야 한다. 이 테스트가 의미 있다는 근거는 **꺼보면 깨진다**는 것이다:

```
$ FDS_TEST_NO_LOCK=1 pytest tests/test_concurrency.py
AssertionError: 잔액으로 감당 가능한 건수(3)보다 많이 성공했다: 11
```

> 마지막 숫자는 돌릴 때마다 달라진다 — 어떤 요청이 어느 시점에 잔액을 읽었는지에
> 달렸기 때문이다. 경합 버그가 재현되지 않는다고 없는 게 아니라는 점이 여기서 보인다.

> 운영 DB는 MySQL이라 `FOR UPDATE`가 실제 행 잠금으로 동작한다. 테스트용 SQLite는
> 행 잠금이 없어 SQLAlchemy가 이 구문을 조용히 버리므로, `conftest.py`가
> `BEGIN IMMEDIATE`로 같은 직렬화 효과를 만든다. `FOR UPDATE` 구문이 실제로 SQL에
> 실린다는 것은 `test_lock_query_emits_for_update`가 따로 검증한다.

## 2-2. 멱등성 키 — 재전송돼도 출금은 한 번

`app/idempotency.py`, `Idempotency-Key` 헤더.

네트워크 타임아웃 뒤 클라이언트가 같은 이체를 다시 보내면, 잠금은 두 요청을 차례로 실행할 뿐이라
두 번 출금된다. 그래서 이체마다 고유한 키를 받아 처음 결과를 기억한다.

- **원자성**: 키 행은 잔액 변경·거래 기록과 **같은 커밋**에 들어간다. 처리 중 예외로 롤백되면 키도 남지 않아
  같은 키로 다시 시도할 수 있다.
- **동시 요청**: 보장은 `(user_id, key)` 유니크 제약이다. 같은 키의 요청이 동시에 오면 하나만 커밋되고, 나머지는
  제약 위반 → 롤백(잔액 변경도 함께) → 먼저 확정된 거래를 돌려받는다. 잠금 전·후의 사전 조회는 최적화일 뿐이다
  — MySQL REPEATABLE READ에서는 스냅샷 때문에 방금 커밋된 키가 조회에 안 보일 수 있다.
- **키 재사용**: 계좌·금액·통화의 해시를 함께 저장한다. 같은 키로 내용이 다른 요청은 409.
- **확정된 실패도 저장한다**: 잔액 부족·대외계 실패도 거래로 기록되므로, 나중에 잔액이 생겨도 같은 키는 같은
  실패를 돌려준다. 재시도로 결과가 바뀌면 클라이언트는 처음 요청의 결과를 알 수 없다.
- 재현된 응답에는 `Idempotent-Replayed: true` 헤더가 붙는다. 키는 선택이다(없으면 매 요청이 새 이체) — 운영
  클라이언트는 반드시 보내야 한다.

**검증** — `tests/test_idempotency.py`: 같은 키로 12건을 동시에 보내면 출금은 정확히 1건, 응답은 12건 모두
같은 거래다. 대조군 두 개로 이것이 무엇 때문에 성립하는지 보인다.
  - 키 기록을 끄면 같은 이체가 **12번** 출금된다 (경합이 실제로 일어났다는 증거)
  - 사전 조회를 전부 무력화해도 1건이다 (보장이 조회가 아니라 유니크 제약에서 나온다는 증거)

## 2-3. 실제 MySQL에서 검증 (Testcontainers, MySQL 8.0 — REPEATABLE READ)

위 SQLite 테스트는 `BEGIN IMMEDIATE`로 DB 전체를 직렬화해 행 잠금을 흉내낸 것이다. `FDS_TEST_DB=mysql`이면 같은
테스트가 운영과 같은 MySQL 컨테이너 위에서 **그대로** 돈다. 여기서 처음으로 `FOR UPDATE` 주장이 실제 엔진에서 확인됐다.

| 확인한 것 | 결과 |
|---|---|
| 동시 이체 12건 — 초과 인출 없음, 금액 보존 (`test_concurrency.py`) | 통과 |
| 같은 멱등성 키 동시 12건 — 출금 1건 (`test_idempotency.py`, REPEATABLE READ 스냅샷에서도 유니크 제약이 보장) | 통과 |
| **대조군: FOR UPDATE를 빼면** 같은 시나리오에서 초과 인출이 일어난다 | 재현됨 |
| **데드락: 계좌 정렬을 끄고** A→B·B→A를 교차로 잠그면 MySQL이 1213으로 하나를 죽인다 / 정렬하면 데드락 없음 | 재현됨 / 없음 |
| 실제 데드락이 난 이체 — 재시도로 두 건 모두 성공, 금액 보존 | 통과 |
| 다른 트랜잭션이 계좌를 쥐고 있으면 잠금 대기 초과(1205) → 재시도 → 503, 출금 없음 → 풀린 뒤 같은 키로 성공 | 통과 |
| 테스트 전체(138건, MySQL 전용 7건 포함) | 통과 |

- **잠금 충돌 처리**: 데드락(1213)·잠금 대기 초과(1205)는 MySQL이 트랜잭션을 롤백한 것이라, 처음부터 다시 실행해도
  이중 출금이 없다. 지수 백오프로 최대 3회 재시도(`TRANSFER_LOCK_RETRIES`)하고, 그래도 안 되면 503을 돌려준다 —
  클라이언트는 같은 멱등성 키로 다시 보내면 된다. 잠금 대기 상한은 InnoDB 기본 50초 대신 5초
  (`MYSQL_LOCK_WAIT_TIMEOUT_SECONDS`). 재시도 횟수는 `transfer_lock_retry_total{reason}` 메트릭으로 남는다.
- **MySQL에서 처음 드러난 버그 — 거래 금액이 잘려 기록됐다.** 거래·보고서의 금액·잔액 컬럼이 SQLAlchemy `Float`였는데,
  MySQL에서는 단정밀도 FLOAT이고 유효숫자 6자리로 돌아온다. **1,234,567원 → 1,234,570원, 12,345.67원 → 12,345.70원.**
  SQLite는 8바이트 실수라 지금까지 모든 테스트가 통과했다. 원장(`accounts.balance`)은 처음부터 `NUMERIC(18,2)`라 잔액
  자체는 정확했지만, 거래 기록과 STR 보고서의 금액이 틀렸다. 금액은 `NUMERIC(18,2)`, 점수·임계값은 `DOUBLE`로 바꿨다
  (`tests/test_money_precision.py` — `Float`로 되돌리면 MySQL에서 실패함을 확인). 기존 DB는
  `scripts/migrations/2026-10-03_money_columns_decimal.sql`로 바꾼다. 이미 잘린 값은 거래 기록 안에서는 복구되지 않지만
  (이체 전후 잔액 컬럼도 같은 FLOAT였다), 감사 로그 detail에 원 단위 정수로 남은 요청 금액으로 원화 거래는 복구할 수 있다.
- **API 경계도 고쳤다**: 요청 금액을 `float` 대신 `Decimal`(소수 둘째 자리까지)로 받는다. 예전에는 100.005원을 받으면
  원장은 100.01원을 옮기고 거래 기록에는 반올림 전 값이 들어가 DB가 따로 반올림했다. 이제 거부(422)하고, 거래 기록·감사
  로그에는 원장과 같은 정규화된 금액을 남긴다. 응답 금액은 JSON 숫자 그대로다(유효숫자 15자리까지 소수 둘째 자리 단위로 정확).
- **재시도와 메트릭**: 재시도는 DB 변경을 롤백하지만 Prometheus 카운터는 롤백되지 않는다. 거래 건수(`transaction_total`)는
  커밋 뒤에만 세므로 재시도가 있어도 한 번이다(MySQL 데드락 재시도 테스트가 확인). 재시도 횟수는 별도 메트릭에 남는다.

## 2-4. 복식부기 엔트리와 대사

`ledger_entries`, `app/reconciliation.py`, `python scripts/reconcile.py`.

잔액 컬럼(`accounts.balance`)은 그대로 두고, 돈이 움직일 때마다 근거를 추가 전용 테이블에 두 행씩 남긴다.
성공한 이체는 출금 −금액·입금 +금액, 계좌 개설은 시스템 자본 계정 −개설금액·새 계좌 +개설금액. 엔트리는 잔액 변경과
**같은 커밋**에 들어간다. 대사 스크립트는 세 가지를 검사하고, 불일치는 고치지 않고 보고만 한다(종료 코드 1).

1. 분개마다 엔트리 합이 0인가 — 한쪽 다리만 남았으면 돈이 생기거나 사라진 것이다
2. 계좌 잔액이 엔트리 누적과 같은가 — 잔액 컬럼이 분개 없이 바뀌었다는 뜻이다(직접 UPDATE, 버그, 위변조)
3. 보류 계정의 엔트리 누적이 보류 중인 거래 금액 합과 같은가 — 보류가 두 번 풀렸거나 상태만 바뀌었다는 뜻이다(2-5)

검증(`tests/test_reconciliation.py`, SQLite·MySQL): 동시 이체 12건 뒤에도 일치한다. **잔액을 일부러 1,000원 올리면**
그 계좌가 정확한 차이와 함께 보고되고, **분개의 한쪽 다리를 지우면** 분개 불균형과 잔액 불일치가 함께 보고된다.
합이 0이 아닌 분개는 기록 시점에 거부한다. 스케줄러는 두지 않았다.

## 2-5. 임시조치 — 고위험 이체 보류 (`app/holds.py`)

예전에는 HIGH 등급이어도 이체가 실행되고 알림·STR 초안만 생겼다. 이제 룰 점수 HIGH(70점 이상) 이체는 입금하지 않고 보류한다.

**조문과 구현 단위의 차이.** 통신사기피해환급법 제2조의5(이용자계좌등에 대한 임시조치)의 대상은 **계좌**다 — 피해의심거래
계좌로 추정되면 "해당 이용자 계좌등의 전부 또는 일부"에 대해 이체·송금·출금을 지연하거나 일시 정지한다(제1항). 그리고
지체 없이 이용자에게 통지하고 본인확인조치를 하며(제2항), 확인 결과 해당하지 않으면 해제하고(제3항), 그 내역을 보존한다(제4항).
이 시스템은 그 취지를 **이체 한 건 단위의 보류**로 구현했다. 계좌 단위 지급 정지, 이용자 통지, 본인확인으로 해제하는 경로는
구현하지 않았다. 24시간 만료도 조문에 없는 이 시스템의 선택이다(조문에는 기간이 없다). 만료 시 돈은 수취인이 아니라 출금
계좌로 돌아간다. 법령명(2026년 개정으로 '피해자산 환급'), 법률 제22047호, 시행일 2026.10.2.는 국가법령정보센터에서 확인했다.

```
이체 요청 ─ 룰 점수 HIGH ─▶ held (202)   출금 계좌 → 보류 계정        분개 HOLD-<id>
                              ├ 승인    ▶ success    보류 계정 → 입금 계좌   분개 RELEASE-<id>
                              ├ 취소    ▶ cancelled  보류 계정 → 출금 계좌   분개 CANCEL-<id>
                              └ 시간 초과 ▶ cancelled  (취소와 같음, 만료 작업자 app.hold_expiry)
```

- **가용 잔액과 원장 잔액**: 보류 금액은 보류 시점에 출금 계좌 잔액에서 빠져 시스템 계정 `SYS-FDS-HOLD`로 간다.
  `accounts.balance`가 곧 가용 잔액이고, 계좌 조회 응답의 `held_amount`를 더하면 원장 잔액이다. 잔액 검사가 기존 이체와 같은
  잠금 구간에서 일어나므로 보류 중인 돈을 다른 이체가 다시 쓸 수 없다. 별도의 "가용 잔액" 컬럼을 두지 않고 기존 복식부기와
  대사를 그대로 쓴다.
- **한 번만 풀린다**: 해제는 `UPDATE transactions SET status=... WHERE id=? AND status='held'`로 상태부터 바꾸고, 1행을 바꾼
  요청만 돈을 옮긴다. 상태 변경·잔액 이동·분개는 한 커밋이다. MySQL의 UPDATE는 스냅샷이 아니라 최신 커밋 값으로 WHERE를 다시
  평가하므로 REPEATABLE READ에서도 성립한다. 잠금 순서는 거래 행 → 계좌 행(오름차순)이고, 이체 경로는 기존 거래 행을 잠그지
  않아 순환 대기가 없다.
- **멱등성**: 같은 키로 재요청하면 새 이체가 아니라 보류된 그 거래(202)를 돌려준다. 풀린 뒤에는 풀린 상태를 돌려준다.
- **판단**: `POST /transactions/{id}/hold-decision` (RISK_OFFICER, 사유 필수), 결과는 감사 로그에 `RESOLVE_HOLD_APPROVE` /
  `RESOLVE_HOLD_CANCEL` / `EXPIRE_HOLD`로 남는다. 보류 시간은 `FDS_HOLD_TTL_HOURS`(기본 24).
- **만료 작업자**: 대사와 달리 만료는 아무도 돌리지 않으면 돈이 무기한 묶인다. 그래서 `docker-compose.yml`에 `hold-expirer`
  서비스(`python -m app.hold_expiry --every 300`)를 상시로 둔다. 여러 개를 띄워도 같은 상태 조건 UPDATE가 중복 처리를 막는다.
- **판단 근거는 룰 점수만**: ML 앙상블 점수는 커밋 뒤에 계산되므로(기본은 꺼져 있다) 보류 여부에 쓰지 않는다.
- **하지 않은 것**: 추가 본인확인(ARS·OTP 재인증)으로 보류를 푸는 경로, 알림 검토(`/fds/alerts/{id}/review`)와 보류 판단의
  연동(지금은 담당자가 둘을 따로 처리한다), 계좌 단위 조치. 본인확인 경로가 왜 필요한지는 아래 오탐 비용이 보여 준다.

**보류의 오탐 비용** (`python -m calibration.hold_cost --source paysim --csv ...`, 운영과 같은 `evaluate_signals`)

보류가 생기면서 점수의 의미가 달라졌다. 전에는 오탐이 담당자의 검토 시간만 썼지만, 이제는 정상 고객의 돈을 최대 24시간 묶는다.
그래서 "보류된 거래 중 몇 건이 정상인가"를 구간별로 셌다.

| 구간 | 보류 비율 | 보류 건수 | 그중 정상 | 보류 100건 중 정상 | 사기 중 보류(재현율) |
|---|---:|---:|---:|---:|---:|
| 1~9일 (룰 결정) | 0.305% | 3,742 | 1,985 | 53.0 | 0.721 |
| 10~12일 (검증) | 0.306% | 1,539 | 918 | 59.6 | 0.738 |
| **13~17일 (평가)** | **0.285%** | **2,527** | **1,553** | **61.5** | **0.744** |
| 18~31일 (참고, 사기 비율 2.3%) | 1.994% | 3,082 | 343 | 11.1 | 0.756 |

- **정상 보류의 거의 전부가 한 조합에서 나온다.** 평가 구간 정상 보류 1,553건 중 1,550건이 `BALANCE_DRAIN 45 + DEST_EMPTY 15
  + NEW_RECIPIENT 10 = 정확히 70점`이고, 이 조합의 정밀도는 25.6%다. 고액 룰이 하나라도 붙은 나머지 조합은 정밀도 95~100%다.
  이 조합은 "잔액 전부를 입금 이력도 잔액도 없는 새 계좌로" — [탐지 문서 3절](detection.md)이 정상 거래에도 흔하다고 경고한 본인 새 계좌 이동과 같은 모양이다.
- **실제 데이터에서는 더 나쁠 것이다.** BALANCE_DRAIN의 lift는 PaySim의 합성 특성(사기는 잔액을 정확히 비운다)에 기대므로,
  원화 운영 데이터에서는 이 조합의 정밀도가 25.6%보다 낮을 가능성이 크다.
- **그래서 본인확인 경로가 필요하다.** 보류 대부분이 정상이라면, 담당자 판단만 기다리게 하는 대신 고객이 추가 인증으로 스스로
  푸는 경로가 있어야 정상 고객의 대기 시간이 줄어든다. 조문(제2조의5 제2·3항)이 요구하는 것도 같은 구조다.
- **임계값은 바꾸지 않았다.** 이 조합만 보류에서 빼면(알림만) 평가 구간 정상 보류가 1,553 → 3건으로 줄고 재현율은 0.744 → 0.337로
  떨어진다. 다만 그 판단을 평가 구간을 보고 내리면 평가 구간이 오염된다. 같은 양상은 룰 결정 구간(1~9일, 조합 정밀도 32.9%)에서도
  보이므로, 바꾼다면 그 구간을 근거로 정하고 평가는 다른 구간에서 다시 해야 한다.

**검증** (`tests/test_holds.py`)

| 확인한 것 | SQLite | MySQL |
|---|---|---|
| HIGH 이체 → 202 held, 출금 계좌에서만 빠지고 입금 없음, `HOLD-` 분개 2행, 대사 일치 | 통과 | 통과 |
| 잔액 1억에 3천만 원 보류 12건 동시 → 보류 3건, 나머지 잔액 부족 (보류 금액이 가용 잔액에서 빠짐) | 통과 | 통과 |
| 승인 6건·취소 6건 동시 → 200 한 건, 409 열한 건, 돈은 한쪽으로만 (상태 변경 직후 지연을 넣어도) | 통과 | 통과 |
| **대조군: 상태를 먼저 읽고 나중에 쓰면** 동시 요청이 둘 다 'held'를 보고 두 번 풀린다 → 대사가 보류 계정 불일치로 잡음 | — (SQLite 테스트는 트랜잭션 전체가 직렬화돼 재현 안 됨) | 재현됨 |
| 같은 멱등성 키 재요청 → 같은 보류 거래, 출금 1회 / 승인 뒤 재요청 → 승인된 상태 | 통과 | 통과 |
| 시간 초과 → 출금 계좌로 반환, 이후 판단은 409 / 만료 작업자 진입점(`app.hold_expiry`)이 실제로 처리 | 통과 | 통과 |

## 2-6. 부하 테스트 — 진단, 인덱스, 100만 행에서 재측정

`scripts/loadtest/`. 이체 시나리오(계좌 200개 사이 무작위 이체 1천~3만 원, 동시 작업자 20, 측정 30초, 워밍업 5초 제외),
노트북(12 논리 코어, Docker Desktop 위 MySQL 8.0)에서 uvicorn 단일 프로세스. 구성을 끄는 것은 운영 코드에 스위치를 넣지 않고
부하 테스트 서버가 해당 함수만 바꿔 끼운다. 운영 처리량이 아니라 **구성 간 상대 비용**을 보기 위한 측정이다.

**1단계 — 비용 진단** (`run_all.sh 20 30`, 거래 테이블 3~4천 행, 구성마다 새 컨테이너·1회 측정)

| 구성 | 처리량 (req/s) | p50 | p95 | p99 | 오류 |
|---|---:|---:|---:|---:|---:|
| 기본 | 84.6 | 224ms | 337ms | 421ms | 0 |
| 감사 해시 체인 끔 | 108.6 (+28%) | 177ms | 254ms | 300ms | 0 |
| FDS 채점 끔 | 100.5 (+19%) | 187ms | 287ms | 363ms | 0 |

- **감사 해시 체인이 가장 큰 비용이다.** 모든 기록이 `audit_chain_head` 한 행을 `FOR UPDATE`로 거쳐 가므로 전역 직렬화 지점이다.
- **동기 FDS 채점은 19%였다.** 그런데 채점 쿼리 3개(송금 계좌 10분 건수, 수취 계좌 24시간 입금 수, 최근 50건 실패율)가 쓰는
  `transactions` 컬럼에 인덱스가 없어 셋 다 전체 스캔이었다. 테이블이 작아 비용이 작게 보였을 뿐이다.

**2단계 — 인덱스 추가 후 100만 행에서 전후 비교** (`run_large.sh 3 20 30 1000000`)

과거 거래 100만 행(계좌 20만 개, 최근 30일)을 채운 컨테이너 하나에서 세 구성을 **번갈아 3회씩** 쟀다(평균 ± 표준편차).
인덱스는 `(account_from, created_at)`, `(account_to, created_at)`, `(created_at, id)` — 기존 DB는
`scripts/migrations/2026-11-17_transactions_scoring_indexes.sql`.

| 구성 | 처리량 (req/s) | p50 | p95 | p99 | 오류 |
|---|---:|---:|---:|---:|---:|
| 인덱스 없음 | 11.4 ± 0.9 | 1,683 ± 124ms | 2,502 ± 283ms | 3,022 ± 311ms | 0 |
| **인덱스** | **83.6 ± 1.6** | **225 ± 6ms** | **355 ± 5ms** | **436 ± 10ms** | 0 |
| 인덱스 + 이체 10% 보류 | 81.7 ± 6.3 | 232 ± 18ms | 358 ± 26ms | 446 ± 40ms | 0 |

```
EXPLAIN (100만 행)                 인덱스 없음                      인덱스
FAILURE_RATE  최근 50건             ALL  993,925행 + filesort   →  index (created_at,id)       50행, 역방향 스캔
VELOCITY      송금 계좌 10분         ALL  993,925행              →  range (account_from,created_at) 1행
NEW_RECIPIENT 수취 계좌 24시간       ALL  993,925행              →  range (account_to,created_at)   1행
```

- **인덱스가 없으면 100만 행에서 처리량이 7분의 1이 된다** (11.4 → 83.6 req/s, p95 2.5초 → 0.36초). 이체마다 쿼리 3개가
  각각 약 99만 행을 읽었다. 인덱스를 두면 100만 행에서도 3~4천 행일 때(84.6 req/s, p95 337ms)와 같은 수준이다 — 채점 비용이
  더 이상 테이블 크기에 비례하지 않는다.
- **보류 경로의 추가 비용은 측정 편차 안이다.** 이체의 10%를 HIGH로 올려(`hold-10pct`, 대외계 실패 시뮬레이션이 먼저 걸린 건은 보류되지 않아 실제 보류는 응답의 약 8%) 보류 분개·
  FDS 알림·STR 초안을 만들게 해도 처리량 81.7 ± 6.3, p95 358 ± 26ms로 인덱스 구성과 구분되지 않는다.
- **측정 뒤 점수에 쓰지 않는 조회를 뺐다.** FAILURE_RATE(최근 50건 실패율)는 시스템 신호라 거래 점수에 들어가지 않는데 이체마다
  조회하고 있었다. 이제 이체 경로에서는 세지 않는다(`collect_signals(include_system_signals=False)`, 테스트로 고정). 실패율
  모니터링은 `GET /fds/stats`가 한다. 위 수치는 그 조회가 남아 있던 상태에서 잰 것이다.
- 남은 비용은 1단계의 감사 체인 직렬화다. 다중 프로세스에서 이 병목이 어떻게 커지는지는 아직 재지 않았다.
- 한계: 반복 3회는 편차를 보여 주기엔 적다. 과거 거래에는 부하 테스트 계좌(LT-*)의 이력을 넣지 않아 채점 결과는 구성 간에 같지만,
  그 계좌들의 실제 이력이 많으면 인덱스 범위 스캔이 읽는 행도 늘어난다.
