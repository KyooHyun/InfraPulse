# 임계값 캘리브레이션

FDS 룰의 임계값과 등급 경계(40점·70점)에 근거를 붙이는 도구.

> **현재 룰은 이 문서가 진단한 룰이 아니다.** 아래 내용은 예전 룰(HIGH_VALUE 10만·FAILURE_RATE·VELOCITY)의 진단
> 기록이다. 그 진단(AUC 0.547, 룰만으로 HIGH 도달 불가)에 따라 룰을 거래 전 사기 신호로 교체했다. 새 룰의 임계값·가중치는
> `python -m calibration.weights`가 PaySim 1~9일로 정한다. 결과와 평가는 [`evaluation/README.md`](../evaluation/README.md).

이 디렉터리는 `financial-risk-detector`(OpenDART 재무위험 탐지) 프로젝트의
`calibration/` 패키지를 이식한 것이다. 그 프로젝트에서 같은 문제 — "수기로 정한 점수
40/30/25/20에 근거가 없다" — 를 lift 측정과 Information Value 구간화로 풀었고,
InfraPulse에도 같은 문제가 그대로 있었다. 도구를 다시 만들 이유가 없어 옮겨왔다.

## 왜 필요한가

`app/fds_engine.py`의 기본값은 전부 금융 상식으로 정한 판단치다.

| 값 | 무엇 | 근거 (2026-09-20 갱신) |
|---|---|---|
| 100,000원 | HIGH_VALUE 임계값 | 부분 — 곡선 맨 아래(거래 69.8% 탐지, lift 1.14). 통화 단위가 달라 원화 값의 근거는 아니다 |
| 0.3 | FAILURE_RATE 임계값 | 없음 — PaySim에 성공/실패 상태가 없어 측정 불가 |
| 5건 / 10분 | VELOCITY 임계값 | 없음 — PaySim에 반복 거래 계좌가 없어 측정 불가 |
| 30 / 25 / 20 / 15 / 10 | 룰 가중치 | 없음 — 신호 하나만 측정돼 순위 비교가 성립 안 함 |
| 40점 | MEDIUM 경계 (검토 대기) | 근거 생김 — 277만 건 중 해당 거래 0건 |
| 70점 | HIGH 경계 (STR 자동 생성) | 근거 생김 — 룰 전용 구성에서 도달 불가 (산수 + 실측) |

"고액거래가 고빈도거래보다 위험하다"는 방향은 맞을 수 있다. 그 배수가 왜 3배여야
하는지가 근거 없는 부분이다.

## 구성

| 파일 | 하는 일 | 데이터 필요 |
|---|---|---|
| `reachability.py` | 점수 공간 도달 가능성 — 임계값에 애초에 닿을 수 있는가 | **불필요** |
| `rule_lift.py` | 룰별 lift, 임계값 곡선, 룰 간 중복 | 필요 |
| `threshold.py` | 임계값 스윕, 비용 민감도, IV 기반 등급 경계 재설정 | 필요 |
| `dataset.py` | 라벨 데이터 → 룰 신호 (DB / PaySim / CreditCard) | — |
| `metrics.py` | 혼동행렬, AUC, lift, 분위수 | — |
| `rules.py` | DB 없이 운영과 같은 룰 집합 만들기 | — |

분석은 운영과 **같은 함수**(`app.fds_engine.evaluate_signals`)로 점수를 낸다.
분석용으로 룰을 다시 구현하면 "분석에서 근거를 확인한 룰"과 "운영에서 도는 룰"이
조용히 갈라진다.

## 1. 데이터 없이 나오는 결론 (이미 확인됨)

```bash
python -m calibration.reachability
```

위험점수는 트리거된 룰의 가중치 합이다. 그러므로 거래 한 건이 받을 수 있는 최대
점수는 정해져 있고, 이건 통계가 아니라 산수다. 표본도 가정도 필요 없다.

### 발견 1 — 선언된 가중치 100점 중 35점은 거래 점수에 못 들어간다

| 룰 | 가중치 | 거래 점수 기여 |
|---|---:|---|
| HIGH_VALUE | 30 | 예 |
| FAILURE_RATE | 25 | 예 |
| VELOCITY | 10 | 예 |
| LOGIN_FAILURE | 20 | **아니오** — 인증 경로에서 처리 |
| LATENCY | 15 | **아니오** — 미들웨어에서 처리 |

`fds_rules` 테이블에는 룰 5개가 총 100점으로 들어 있어 "100점 만점"처럼 보이지만,
거래 한 건이 실제로 받을 수 있는 최대 점수는 **65점**이다.

### 발견 2 — HIGH(70점) 등급은 룰만으로는 도달 불가능하다

```
HIGH_VALUE + FAILURE_RATE + VELOCITY = 30 + 25 + 10 = 65 < 70
```

ML 앙상블을 끈 구성에서는 **어떤 거래도 HIGH가 될 수 없다.** 그 경계에 걸린
STR(의심거래보고서) 자동 생성은 실행되지 않는 코드다.
README에 적힌 "위험점수 70점 이상 거래에 STR 자동 생성"은 룰 전용 구성에서 사실이 아니었다.

ML을 켜면 상한이 달라진다. `ensemble = α·(rule/100) + (1−α)·if_score`, α=0.5이므로
룰 65점 기준 최대 **82.5점**이고 HIGH에 도달한다. (PaySim처럼 FAILURE_RATE·VELOCITY가 발화하지
않는 데이터에서는 룰 상한이 30점이라 앙상블 상한도 65점이다.) 즉 **같은 임계값 70점이 두 구성에서 다른 의미를
갖는다** — 한쪽에서는 "매우 위험", 다른 쪽에서는 "발생 불가".

### 발견 3 — 고액이 아닌 이상거래는 검토 대기열에 오르지 못한다

```
FAILURE_RATE + VELOCITY = 25 + 10 = 35 < 40 (MEDIUM)
```

HIGH_VALUE가 발화하지 않으면 나머지 룰에 전부 걸려도 MEDIUM에 못 미친다.
소액 분할 이체처럼 금액을 낮춰 빠져나가는 전형적 수법이 구조적으로 검토 대상에서
빠진다는 뜻이다.

### 이 발견들로 한 것 / 하지 않은 것

**한 것** — `app/routers/transactions.py`에서 STR 판정이 알림에 기록된 점수와
다른 점수를 쓰던 불일치를 고쳤다. 알림에는 앙상블 점수를 적으면서 STR은 룰 점수로
판정해서, 알림에 70점 넘는 점수가 찍혀도 STR이 생성되지 않았다.

**하지 않은 것** — 임계값과 가중치는 건드리지 않았다. 70점을 65점으로 내릴지,
가중치를 올릴지, 룰을 더할지는 산수가 아니라 데이터가 정할 일이다. 근거 없는
숫자를 근거 없는 다른 숫자로 바꾸는 건 문제를 옮기는 것일 뿐이다.

이 상태는 `tests/test_calibration.py::test_known_gap_rule_only_config_cannot_reach_high`
가 고정하고 있다. 결정이 내려져 그 테스트가 실패하면 README도 같이 고쳐야 한다.

## 2. 데이터가 있을 때

### 데이터셋 받기

`evaluation/data/`는 `.gitignore` 대상이다. 아래 중 하나를 받아 넣는다.

- PaySim — <https://www.kaggle.com/datasets/ealaxi/paysim1>
  계좌 식별자와 시각이 있어 HIGH_VALUE·VELOCITY 두 신호를 만들 수 있다.
- ULB Credit Card Fraud — <https://www.kaggle.com/datasets/mlg-ulb/creditcardfraud>
  계좌 식별자가 없어 HIGH_VALUE 하나만 나온다. 금액 임계값만 볼 때 쓴다.

> PaySim은 `evaluation/README.md`에서 **ML 앙상블 평가용으로는** 부적합하다고 판정했다
> (룰 탐지 집합 내 IF 분리도 불량). 그건 Isolation Forest의 변별력에 대한 판정이고,
> 여기서 묻는 것은 "금액 임계값을 어디에 둘 때 lift가 높은가"라 질문이 다르다.
> 금액·계좌·시각 구조가 필요한 이 분석에는 PaySim이 맞다.

### 실행

```bash
# DB에 적재한 뒤 DB에서 (권장 — 운영과 같은 경로로 신호를 만든다)
python scripts/load_paysim.py evaluation/data/PS_20174392719_1491204439457_log.csv --limit 300000
python -m calibration.rule_lift --source db
python -m calibration.threshold --source db

# CSV에서 바로
python -m calibration.rule_lift  --source paysim --csv evaluation/data/PS_...log.csv --limit 300000
python -m calibration.threshold  --source paysim --csv evaluation/data/PS_...log.csv --limit 300000
```

산출물은 `calibration/outputs/` (gitignore 대상).

### 측정 결과 (PaySim 전체 2,770,409건, 2026-09-20 실행)

`isFraud` 라벨이 TRANSFER/CASH_OUT 유형에만 있으므로 그 두 유형만 읽는다.
표본 사기율 0.296%(8,213건). 30만 건 부분표본 결과는 괄호로 병기한다.

**HIGH_VALUE 임계값 10만 — 곡선의 맨 바닥에 있다**

| 임계값 | 탐지율 | 정밀도 | 재현율 | lift |
|---:|---:|---:|---:|---:|
| **100,000 (현행)** | **69.8%** | 0.0034 | 0.792 | **1.14** (30만 표본: 0.90) |
| 171,261 | 50.0% | 0.0041 | 0.695 | 1.39 |
| 306,791 | 25.0% | 0.0069 | 0.579 | 2.32 |
| 544,868 | 10.0% | 0.0134 | 0.453 | 4.53 |
| 954,997 | 5.0% | 0.0202 | 0.341 | 6.83 |
| 1,533,557 | 2.5% | 0.0295 | 0.248 | 9.94 |
| 2,650,036 | 1.0% | 0.0475 | 0.160 | 16.04 |
| **4,271,521 (lift 최대)** | 0.5% | 0.0619 | 0.104 | **20.89** |

lift 1.0은 "룰이 아무 정보도 주지 않는다"는 뜻이다. 현행 임계값의 1.14는 거기서
거의 움직이지 않은 값이고, 이유는 표 첫 칸에 있다 — **전체 거래의 69.8%를 탐지한다.**
거의 모든 거래에 발화하는 규칙은 어떤 거래가 위험한지 말해주지 않는다. 사기 거래의
금액 중앙값(239,647)이 정상(180,890)보다 높은데도 lift가 오르지 않는 것은, 임계값이
그 차이가 나타나는 구간보다 한참 아래에 있기 때문이다.

부분표본(30만 건)에서는 같은 값이 **0.90 — 1.0 미만**으로 나온다. 표본을 바꾸면
"무정보"와 "무작위보다 나쁨" 사이에서 부호가 갈린다는 뜻이고, 이 숫자를 한 자리까지
인용하면 안 된다는 근거다. 방향(현행 임계값은 곡선 맨 아래)은 두 표본에서 같다.

**등급 경계 40/70 — 실측으로도 빈 구간이다**

```
등급        거래수      사기      사기율
LOW      2,770,409    8,213    0.2965%
MEDIUM           0        0         -
HIGH             0        0         -
룰 점수 AUC 0.547 (30만 표본: 0.464)
```

`reachability.py`가 산수로 예측한 것이 데이터에서 그대로 나왔다. 이 데이터에서는
FAILURE_RATE·VELOCITY가 한 번도 발화하지 않아 거래가 받을 수 있는 점수가 HIGH_VALUE의
30점뿐이고, 30점은 MEDIUM(40점)에 못 미친다. **277만 건 중 검토 대기열에 오르는 거래가
한 건도 없다.** AUC 0.547은 무작위(0.5)에서 거의 떨어지지 않은 값이다.

비용비를 1에서 200까지 흔들어도 최적 임계값은 31점에서 움직이지 않는다. 점수가
가질 수 있는 값이 {0, 30}뿐이라 그 사이 어디를 잘라도 같은 분할이기 때문이다.
비용 민감도 분석이 의미를 가지려면 점수가 연속적이어야 한다 — ML 앙상블을 켜야
나오는 성질이다.

IV 기반 경계 재설정은 **결과를 내지 못했다.** 단조 증가 + 최소표본 30건을 만족하는
경계 조합이 없다. 실패가 아니라 입력이 부족한 것이다: 점수가 두 값뿐인데 세 구간으로
나눌 수는 없다.

### 이 측정으로 답한 것 / 여전히 못 답한 것

| 숫자 | 상태 |
|---|---|
| 40점·70점 등급 경계 | **근거 생김** — 현행 룰 구성에서 두 경계 모두 빈 구간이라는 것이 산수와 실측 양쪽에서 확인됐다 |
| 10만원 HIGH_VALUE | **부분적** — 임계값 곡선에서 맨 바닥이라는 위치는 나왔다. 다만 아래 통화 단위 문제 때문에 "원화 10만원"의 근거는 아니다 |
| 30% FAILURE_RATE | **여전히 근거 없음** — PaySim에 거래 성공/실패 상태가 없어 측정 자체가 불가능하다 |
| 5건/10분 VELOCITY | **여전히 근거 없음** — PaySim은 송금 계좌 2,768,630개 중 2회 이상 등장하는 것이 1,776개(최대 3회)뿐이라 이 룰이 구조적으로 발화할 수 없다. 탐지수 0은 룰에 대한 판정이 아니라 데이터에 대한 판정이다 |

임계값과 가중치는 이번에도 **바꾸지 않았다.** 위 표에서 근거가 생긴 것은 "현행 값이
곡선 맨 아래에 있다"는 사실까지이고, 그럼 얼마로 옮길지는 탐지 누락 비용과 검토 공수의
비율이 정한다. 그 비율은 이 저장소에 없는 숫자다.

## 한계

- **표본 내 최적화**: 임계값을 표본 전체에서 고르면 그 표본에 과적합된다.
  기간을 나눠 앞에서 고르고 뒤에서 검증하는 out-of-time 검증이 다음 단계다.
- **모집단 사기율 가정**: `threshold.py`의 `POPULATION_FRAUD_RATE = 0.001`은
  얇은 가정이다. 그래서 비용비를 흔들어 결론이 얼마나 버티는지 함께 낸다.
- **통화 단위가 다르다**: PaySim의 `amount`는 원화가 아니다(출처 논문에 통화 단위가
  명시돼 있지 않다). 그래서 위 곡선은 "현행 임계값이 이 분포의 어디쯤에 있는가"는
  말해주지만, **"원화 10만원이 옳은 값인가"에는 답하지 못한다.** 곡선에서 읽어야 할
  것은 절대값이 아니라 위치다 — 거래의 70%를 잡는 지점에 경보를 걸어두고 있다는 사실.
  원화 기준 값을 정하려면 국내 이체 금액 분포가 필요하고, 그 데이터는 아직 없다.
- **PaySim으로는 VELOCITY를 측정할 수 없다**: 송금계좌 299,980개 중 2회 이상 등장하는
  계좌가 20개뿐이라, 창을 아무리 넓혀도 "10분 내 5건"은 물론 "2건"도 거의 발화하지 않는다
  (임계값 1로 내려야 전건 탐지 = lift 1.00). 측정 결과의 탐지수 0은 룰이 쓸모없다는
  뜻이 아니라 **이 데이터로는 질문에 답할 수 없다**는 뜻이다. 반복 거래 계좌가 있는
  데이터가 따로 필요하다.
- **PaySim으로는 FAILURE_RATE도 측정할 수 없다**: 거래 성공/실패 상태 자체가 없다.
- **표본 크기에 따라 결론이 흔들린다**: 같은 HIGH_VALUE lift가 30만 건에서 0.90,
  277만 건에서 1.14다. 앞쪽 30만 건은 초반 step만 보는 시간 절단 표본이기 때문이다.
  임계값 결정에 쓰려면 기간을 나눠 검증하는 out-of-time 절차가 선행돼야 한다.
