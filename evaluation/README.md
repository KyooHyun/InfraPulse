# FDS 성능 평가

## 평가 방법 — 운영 엔진으로 잰다

```bash
python scripts/train_model.py --source paysim --csv evaluation/data/PS_20174392719_1491204439457_log.csv
python scripts/evaluate.py    --source paysim --csv evaluation/data/PS_20174392719_1491204439457_log.csv
```

평가 스크립트는 점수를 직접 계산하지 않는다. 모든 구성 요소를 운영 코드에서 import한다.

| 구성 요소 | 정의 위치 (유일) |
|---|---|
| 룰 점수 | `app.fds_engine.evaluate_signals` |
| 룰 임계값·가중치 | `app.fds_engine.DEFAULT_RULES` |
| ML 피처 | `app.ml.features.feature_values` |
| IF 원점수 → 0~1 정규화 | `app.ml.isolation_forest.IFModel.anomaly_scores` |
| 앙상블과 α | `app.ml.ensemble.ensemble_score`, `RULE_ALPHA = 0.5` |

신호와 피처의 **원천값을 모으는 쪽**만 둘로 나뉜다. 운영은 거래마다 DB를 조회하고
(`collect_signals`, `extract_features`), 평가는 277만 건을 한 번에 계산한다(`calibration/dataset.py`).
`tests/test_scoring_parity.py`는 같은 거래 300건을 양쪽에 넣어 신호, 룰 점수, ML 피처가 모두
일치하는지 확인한다. 이력에는 동률 시각, 윈도우 경계, 실패율 표본 부족 같은 경계 조건을 일부러 넣었다.
`tests/test_single_source.py`는 위 표의 구성 요소가 다른 파일에 다시 정의되면 실패한다.

## 표본 내 재측정 결과 (PaySim TRANSFER/CASH_OUT, 2,770,409건, 사기 8,213건 = 0.296%)

| 방법 | ROC-AUC | PR-AUC | recall@0.1% | recall@0.5% | recall@1% |
|---|---:|---:|---:|---:|---:|
| 룰 단독 | 0.547 | 0.0033 | 0.001 | 0.006 | 0.011 |
| Isolation Forest | 0.883 | 0.0354 | 0.018 | 0.159 | 0.217 |
| 앙상블 (α=0.5) | 0.794 | 0.0398 | 0.018 | 0.173 | 0.243 |

recall@k%는 점수 상위 k%만 알림으로 보낼 때의 재현율이다. 무작위로 골랐을 때의 기댓값은
k%와 같다(예: recall@0.5%의 기댓값은 0.005). 경계에 걸린 동점 묶음은 그 안에서 무작위로 고를 때의
기댓값으로 셌다.

현행 등급 경계(40/70)에 걸리는 거래:

| 방법 | MEDIUM | HIGH |
|---|---:|---:|
| 룰 단독 | 0 | 0 |
| 앙상블 (α=0.5) | 53,762 | 0 |

**기존 진단이 재현됐다.** 룰 단독 AUC 0.547과 MEDIUM/HIGH 0건은 리팩터링 전 calibration 결과와
같다. calibration은 처음부터 `evaluate_signals`와 `DEFAULT_RULES`를 썼기 때문에, 이 수치는 실제
룰 엔진으로 잰 값이었다. 엔진을 따로 구현해 쓴 곳은 철회한 ULB·PaySim 평가 스크립트 두 개뿐이었다.
이 표가 앞으로 개선할 때의 기준점이다.

### 해석할 때 주의할 점

- **룰 단독은 무작위와 같다.** recall@0.5%가 0.006으로, 무작위 기댓값 0.005와 거의 같다.
  PaySim에서 실제로 동작하는 룰은 HIGH_VALUE(10만, 전체의 69.8%에서 발화)뿐이고, 점수가 가질 수 있는
  값이 {0, 30} 둘뿐이다.
- **IF 수치는 낙관적이다.** 같은 데이터로 학습하고 평가했다(표본 내 평가). 시간 분할 평가를 넣은 뒤에
  다시 재야 한다.
- **IF 피처에 거래 후 정보가 들어 있다.** 9개 피처 중 `balance_orig_after`, `balance_dest_after`,
  `error_orig`, `error_dest`는 이체가 끝난 **뒤**의 잔액으로 계산한다. 운영에서도 ML 점수는 이체를
  기록한 뒤에 매기므로, 지금 구조로는 ML이 이체를 막을 수 없다. 또 PaySim에서 이 잔액 불일치
  피처는 합성 데이터의 특성(사기 거래의 잔액 기록 방식)과 관련이 깊어서 일반화할 수 없을 가능성이
  높다. 거래 전 정보만 쓰는 피처로 다시 재는 것이 다음 작업이다.
- **앙상블의 ROC-AUC(0.794)가 IF 단독(0.883)보다 낮다.** 반면 PR-AUC와 알림 예산 재현율은 조금
  높다. 무정보에 가까운 룰 점수({0, 30})를 절반 가중치로 섞으면서 전체 순위는 흐려지지만, 상위
  구간은 크게 바뀌지 않기 때문이다. "앙상블이 낫다"고 말하려면 시간 분할 평가로 다시 확인해야 한다.
- **앙상블도 HIGH(70점)에는 도달하지 못한다 — 경계 조건이 아니라 구조적으로.** PaySim에서는
  VELOCITY(5건/10분)가 발화하지 않는다(송금 계좌 최대 3회 등장). 그래서 룰 점수 상한은 HIGH_VALUE의
  30점이고, α=0.5에서 앙상블 상한은 0.5·0.3 + 0.5·1.0 = 65점이다. (운영 구성의 82.5점은
  FAILURE_RATE까지 발화할 때의 상한이다.)

## 시간 분할 평가 — 1단계: 분할만 적용 (피처는 그대로)

```bash
python scripts/evaluate.py --source paysim --csv evaluation/data/PS_20174392719_1491204439457_log.csv     --train-until-step 288 --segment-steps 408
```

PaySim의 하루 거래량은 1~17일에 15만~25만 건이다. 그런데 18일부터 수천~2만 건으로 20배 가까이
줄고, 사기는 하루 약 250건으로 그대로다. 그래서 사기 비율이 0.15% → 1~7%로 뛰고, 31일은 100%다.
전체 사기의 40%가 거래량 5%에 해당하는 구간에 몰려 있다. 이 때문에 평가 구간을 둘로 나눴다.

| 구간 | step | 거래 | 사기 비율 |
|---|---|---:|---:|
| 학습 (IF 학습 + 알림 임계값 결정) | 1~288 (1~12일) | 1,729,766 | 0.190% |
| 평가1 (학습 구간과 같은 성격) | 289~408 (13~17일) | 886,056 | 0.148% |
| 평가2 (저거래·고사기율) | 409~743 (18~31일) | 154,587 | 2.344% |

알림 임계값은 학습 구간 점수의 상위 0.5% 지점이고, 평가 구간에는 그 값을 그대로 적용했다.
PR-AUC는 사기 비율에 따라 기준선이 달라진다(무작위 탐지기의 PR-AUC = 사기 비율).

**평가1** (사기 비율 0.148%)

| 방법 | ROC-AUC | PR-AUC | 실제 알림 비율 | 재현율 | 정밀도 |
|---|---:|---:|---:|---:|---:|
| 룰 단독 | 0.545 | 0.0016 | 70.6% | 0.796 | 0.0017 |
| Isolation Forest | 0.875 | 0.0101 | 1.405% | 0.177 | 0.0186 |
| 앙상블 (α=0.5) | 0.793 | 0.0104 | 1.509% | 0.196 | 0.0192 |
| IF (표본 내 대조) | 0.884 | 0.0121 | | | |

**평가2** (사기 비율 2.344%)

| 방법 | ROC-AUC | PR-AUC | 실제 알림 비율 | 재현율 | 정밀도 |
|---|---:|---:|---:|---:|---:|
| 룰 단독 | 0.558 | 0.0265 | 68.9% | 0.803 | 0.0273 |
| Isolation Forest | 0.887 | 0.2400 | 0.904% | 0.169 | 0.4381 |
| 앙상블 (α=0.5) | 0.809 | 0.2575 | 1.005% | 0.194 | 0.4530 |
| IF (표본 내 대조) | 0.895 | 0.2864 | | | |

"표본 내 대조"는 같은 평가 행을 전체 데이터로 학습한 IF로 채점한 값이다. 분할 행과의 차이가
표본 내 평가가 수치를 부풀린 정도다.

**읽은 것**

- **표본 내 평가의 부풀림은 ROC-AUC에서는 작고(약 0.01), PR-AUC에서는 약 16~17%다**
  (평가1 0.0121 → 0.0101, 평가2 0.2864 → 0.2400). 순위 전체보다 상위 구간이 더 부풀려졌다.
- **학습 구간에서 정한 0.5% 임계값이 평가 구간에서 지켜지지 않는다.** 학습 구간과 성격이 같아
  보이는 평가1에서도 IF의 실제 알림 비율은 1.405%로, 예산의 2.8배다. 거래량과 사기 비율이
  비슷해도 IF 점수 분포는 이동한다는 뜻이다. 운영에서 "상위 0.5%"를 고정 임계값으로 두면 검토
  물량이 예산을 넘는다. 임계값을 주기적으로 다시 정하거나, 알림 비율 자체를 감시해야 한다.
- **룰 단독은 알림 예산을 맞출 수 없다.** 점수가 {0, 30} 둘뿐이라 상위 0.5% 지점이 30점이 되고,
  그러면 거래의 약 70%가 알림이 된다.
- 앙상블과 IF는 알림 비율이 서로 달라서(1.509% vs 1.405%) 이 표의 재현율로 우열을 가릴 수 없다.
  "같은 알림 건수에서의 재현율"은 표본 내 표의 recall@k가 보여 주지만, 그것은 표본 내 수치다.
- 이 단계에서는 피처를 바꾸지 않았다. 피처 9개 중 4개가 이체 후 정보라는 문제는 그대로이고,
  2단계에서 거래 전 피처로 바꾼 뒤 다시 잰다. 두 단계를 나눈 것은 수치 변화가 분할 때문인지
  피처 때문인지 구분하기 위해서다.

## 시간 분할 평가 — 2단계: 거래 전 피처로 교체

1단계와 같은 분할(학습 1~12일 / 평가1 13~17일 / 평가2 18~31일)에서 IF 피처만 바꿨다.

### 피처 세트 선택 — 평가 구간을 보지 않고 골랐다

평가 구간 결과를 보고 피처를 고르면 평가 데이터로 튜닝하는 것이 된다. 그래서 학습 구간 안을
다시 나눠(1~9일 학습, 10~12일 검증, 검증 사기 비율 0.167%) 세 세트를 비교했다.

| 피처 세트 | 검증 ROC-AUC | 검증 PR-AUC |
|---|---:|---:|
| 원래 9개 (거래 후 잔액 4개 포함) | 0.882 | 0.0269 |
| **거래 전 5개** — 금액(log), 송금·수취 계좌 거래 전 잔액, 시간대, velocity | **0.905** | **0.1956** |
| 거래 전 5개 + 금액/잔액 비율, 송금 잔액 0 여부, 수취 잔액 0 여부 | 0.897 | 0.0396 |

거래 전 5개를 운영 피처로 정했다(`app/ml/features.py`).

**예상과 달랐던 것 — 거래 후 정보를 빼자 성능이 올랐다.** 거래 후 잔액이 누수처럼 성능을
부풀렸을 것이라고 예상했지만 반대였다. IF는 비지도 모델이라 "사기 = 잔액을 비움"이라는 방향을
모른다. 그래서 거래 후 잔액은 그저 크기가 큰 차원으로 작용해 정상 고액 계좌를 고립시켰다.
누수는 레이블을 보는 모델(룰, 지도학습)에서 생기는 문제였다. 다만 판정 시점에 없는 정보라는
문제는 그대로이므로 제거는 맞다.

**금액/잔액 비율을 넣으면 나빠진 이유 — 합성 데이터의 특성.** PaySim 정상 TRANSFER/CASH_OUT의
47.4%는 거래 전 잔액이 0인데도 송금한다(사기는 0.5%). 그래서 정상 거래의 비율은 중앙값 605,
상위 1%는 176만이라는 극단값을 갖고, 사기는 정확히 1.0이다(잔액을 정확히 비운다). IF는 극단값을
이상으로 보므로 정상 거래를 고립시킨다. 반대로 "금액 = 잔액" 같은 지도 방식 룰은 PaySim에서
사기를 거의 다 잡을 수 있지만, 그것은 시뮬레이터의 잔액 기록 방식 때문일 가능성이 높아서
일반화할 수 없다. 이 신호는 룰 작업에서 이 해석과 함께 다룬다.

### 단계별 변화 (IF, 평가1 기준)

| 단계 | ROC-AUC | PR-AUC | 실제 알림 비율 (예산 0.5%) |
|---|---:|---:|---:|
| 표본 내, 원래 9개 피처 | 0.884 | 0.0121 | — |
| 1단계: 시간 분할, 원래 9개 피처 | 0.875 | 0.0101 | 1.405% |
| 2단계: 시간 분할, 거래 전 5개 피처 | 0.903 | 0.1234 | 0.926% |

**읽은 것**

- **실제 성능의 기준점은 2단계 행이다.** 학습 구간 밖에서, 판정 시점에 있는 정보만으로, 학습 구간에서
  정한 임계값을 그대로 쓴 결과다. 평가1에서 IF는 거래의 0.93%를 알림으로 보내 사기의 40%를 잡는다
  (정밀도 6.4%, 사기 비율 0.148%의 약 43배).
- **표본 내 평가가 항상 부풀리는 것은 아니다.** 2단계에서는 표본 내 대조군의 PR-AUC가 분할 평가보다
  낮다(평가1 0.0968 < 0.1234). 학습 데이터에 성격이 다른 18일 이후 구간이 섞이면 오히려 나빠진다.
  1단계에서 본 "PR-AUC 16~17% 부풀림"은 피처와 학습 데이터 구성에 따라 달라지는 값이라 일반화하지 않는다.
- **알림 비율 드리프트는 여전하다.** 학습 구간에서 0.5%로 맞춘 임계값이 평가1에서 0.93%, 평가2에서 1.54%
  알림을 낸다. 임계값을 주기적으로 다시 정하거나 알림 비율을 감시해야 한다.
- **앙상블이 IF보다 낫다고 말할 수 없다.** PR-AUC는 조금 높고 ROC-AUC는 낮으며, 알림 비율이 달라서
  재현율도 직접 비교할 수 없다. 앙상블에 섞이는 룰 점수가 무작위 수준(AUC 0.545)이기 때문이다.
  룰을 고친 뒤 다시 본다.
- 한계: PaySim은 합성 데이터이고 금액 단위가 원화가 아니다. 이 수치는 "이 구조가 이 데이터에서
  어떻게 동작하는가"이지 원화 운영 환경의 성능이 아니다.

## 시드 민감도 — 피처 세트 선택 재확인

IF는 무작위 표본으로 트리를 만들어 시드에 따라 결과가 흔들린다. 검증 구간(10~12일)에서 시드 5개로 다시 비교했다.

| 피처 세트 | 검증 ROC-AUC | 검증 PR-AUC (평균 ± 표준편차) | 범위 |
|---|---:|---:|---:|
| 원래 9개 | 0.885 ± 0.002 | 0.033 ± 0.009 | 0.024 ~ 0.041 |
| **거래 전 5개** | **0.909 ± 0.004** | **0.218 ± 0.033** | **0.184 ~ 0.261** |
| 5개 + 3개 | 0.898 ± 0.003 | 0.037 ± 0.004 | 0.034 ~ 0.044 |

5개 세트의 최저값(0.184)이 다른 세트의 최고값(0.044)의 4배 이상이다. 피처 세트 간 차이는 시드 편차보다 훨씬 크고,
채택은 유지한다. 다만 5개 세트 자체도 시드에 따라 PR-AUC가 ±15% 흔들리므로, 아래 최종 비교는 시드 5개로 냈다.

## 룰 재설계와 최종 비교

### 규율

룰은 레이블을 보고 만드는 것이라 사실상 지도학습이다. 그래서 IF보다 엄격하게 분할을 지켰다.

| 구간 | 쓰임 |
|---|---|
| 1~9일 | 룰 후보 탐색, 임계값·가중치 결정 (`python -m calibration.weights`) |
| 10~12일 | 검증 — 룰 변형 비교, 알림 임계값 방식 비교 (`--max-step 288`로 13일 이후는 읽지도 않음) |
| 13~17일 | 평가 — **룰은 최초 개봉, 마지막에 한 번만.** 연 뒤에는 아무것도 바꾸지 않았다 |
| 18~31일 | 참고 — 사기 비율 2.3%로 성격이 전혀 다른 구간 |

IF는 13~17일에서 시간 분할 1·2단계 때 이미 측정했으므로 **재측정**이다(피처 선택은 검증 구간에서 했다).
α는 0.5(운영 값) 그대로이고, 데이터로 다시 고르지 않았다.

### 1~9일 탐색에서 본 것

| 후보 | 발화율 | 재현율 | lift |
|---|---:|---:|---:|
| 금액 상위 1% | 1.0% | 0.213 | 21.3 |
| 금액 상위 5~1% | 4.0% | 0.152 | 3.8 |
| 금액 하위 80% | 80% | 0.467 | 0.47~0.65 |
| **금액 = 거래 전 잔액, 잔액 > 0** | 0.195% | 0.980 | **503** (정밀도 100%) |
| 금액 ≥ 거래 전 잔액, 잔액 > 0 | 42.4% | 0.982 | 2.3 |
| 금액이 잔액의 90~100%, 잔액 > 0 (채택한 BALANCE_DRAIN) | 0.95% | 0.981 | 103.5 |
| 수취 계좌 거래 전 잔액 0 | 13.5% | 0.644 | 4.8 |
| 수취 계좌 직전 24시간 입금 0건 | 33.5% | 0.795 | 2.4 |
| 수취 계좌 직전 24시간 입금 5건 이상 | 13.0% | 0.030 | 0.23 |

- "금액 = 잔액" 하나로 정밀도 100%, 재현율 98%가 나온다. 조건을 "금액 ≥ 잔액"으로 조금만 넓혀도 lift가 2.3으로
  떨어진다. 정확한 일치 자체가 시뮬레이터의 흔적이다.
- 수취인 입금 건수는 예상과 반대 방향이었다. 입금을 많이 받는 계좌는 오히려 안전하고(lift 0.23), 위험 신호는
  **입금이 없던 신규·휴면 수취인**이다. 송금 계좌가 거의 한 번씩만 등장해 "서로 다른 송금인 수"는 입금 건수와 같은
  값이 되어 따로 측정할 수 없다. 입금 직후 출금 연쇄(수취 계좌 → 현금화 계좌)도 PaySim에서는 계좌가 연결되지 않아
  측정하지 못했다.

### 결론

1. **룰은 무작위 수준을 벗어났다.** BALANCE_DRAIN을 빼도 ROC-AUC 0.810, 같은 예산 재현율 0.164
   (무작위 0.005의 33배). 이전 룰은 AUC 0.545였다.
2. **BALANCE_DRAIN을 넣은 수치는 성능으로 주장하지 않는다.** 재현율 0.803은 "사기는 잔액을 정확히 비운다"는 PaySim
   특성에 기댄 값이다. 실제로는 본인 계좌 간 이동처럼 잔액을 전부 옮기는 정상 거래가 흔하다. 그런데 HIGH 등급은 이
   룰이 있어야만 도달하므로, 운영 전에 원화 데이터로 반드시 재보정해야 한다.
3. **앙상블 vs IF:** PR-AUC로는 앙상블이 낫다(DRAIN 제외 0.291 vs 0.145, 시드 편차 0.029보다 훨씬 큰 차이).
   하지만 **예산 0.5% 지점의 재현율은 0.353 vs 0.341로, 차이가 시드 편차 수준이라 구분되지 않는다.** 검토 인력이 정해진
   운영 관점에서는 앙상블의 이점이 입증되지 않았다.
4. **DRAIN을 포함하면 앙상블(0.636)이 룰 단독(0.803)보다 나쁘다.** 강한 룰 점수에 IF를 절반 섞으면 상위 순위가 흐려진다.
   α=0.5는 이 상황에 맞지 않는다는 뜻이지만, 평가 구간을 연 뒤라 여기서 α를 고르지 않았다.
5. **알림 임계값은 직전 1일 분위수로 매일 갱신하는 것이 안정적이다.** 세 구간 모두 0.53~0.69%였다. 고정 임계값은 구간에
   따라 0.41~2.7%로 예측할 수 없었다. 단, 분포가 그대로인 검증 구간에서는 갱신 방식이 고정보다 약간 많이 알림을 냈다.

## 이전 결과 철회

이 디렉터리에는 ULB Credit Card Fraud 데이터셋(n=284,807, fraud=492)으로 "룰 단독 vs
룰+Isolation Forest 앙상블"을 비교해 **FPR ▼50%, Recall ▼0.41%p**라고 적은 결과가 있었다.
이 수치는 철회했고, 해당 스크립트(`creditcard_eval.py`, `paysim_eval.py`)는 삭제했다. 철회 이유:

1. **기준선이 실제 엔진이 아니었다.** 두 스크립트는 `app/fds_engine.py`를 호출하지 않고
   `Amount >= p95 → 45점` 룰을 스크립트 안에서 따로 구현했다. 실제 HIGH_VALUE는 30점이라
   단독으로는 MEDIUM(40점)에도 못 미친다.
2. **α와 IF 정규화가 운영과 달랐다.** 두 스크립트 모두 `IF_ALPHA = 0.4`를 썼다(paysim_eval.py의
   docstring에는 0.6이라고 적혀 있어 문서와 코드도 어긋나 있었다). 운영은 0.5다. IF 원점수를
   0~100으로 바꾸는 정규화도 스크립트마다 따로 구현했다.
3. **비교 방식이 주장을 뒷받침하지 못한다.** FPR 절반 감소는 임계값만 올려도 얻을 수 있다.
   Recall 8.74%는 사기 492건 중 약 43건을 잡았다는 뜻이기도 하다.

`GET /fds/comparison`은 여전히 `{"status": "pending"}`을 반환한다. 위 결과는 무작위 수준의 룰과 비교한 것이라, 룰을 고친 뒤의 비교를 공개한다.
